Development notes · Stillroom 0.10 · 20 October 2026

A 3D rendering
core in Haskell

The main view, shadows and water reflections depict one world from different viewpoints. Defining that relationship with pure values helped us fix disagreements between them.

Stillroom is a Windows app for music while working and scenery during breaks. Its renderer uses Haskell, raylib and GLSL.

01 / Comparison

Fixing flicker on a moving railcar

The railcar's surfaces and shadows flickered as it moved. Version 0.10 addresses overlapping faces, coordinate rounding, and inconsistent geometry and projections across passes. Both films below use the same place, timestamps and High quality setting.

Geometry

Remove duplicate surfaces

Keep the railcar's dimensions and colours. Remove internal contact faces and coincident exterior faces, so two surfaces no longer compete for the same depth.

Precision

Use a nearby origin

Subtract a nearby origin from large world coordinates in Double, then convert to Float. This avoids losing small positional differences before subtraction.

Shadows

Share the geometry and projection

Keep terrain selection consistent across passes. Anchor the shadow grid in light space and account for the receiving surface's slope before filtering visibility.

02 / Design

Separate terrain selection from the viewing camera

A shadow cannot line up with the ground if its pass draws a different ground surface. Previously, the current rendering camera also selected terrain detail. Switching to the light or reflection camera could change the terrain's height.

The new frame plan fixes a geometry-selection reference and clock first. The passenger, light and reflected camera then observe that world. A shared Haskell value carries the agreement into each pass.

The pure boundary

Return a frame plan as a value

Given the current world and the dimensions of targets actually allocated by the GPU, planFrame returns a plan containing its projections. Invalid inputs return an error.

This calculation does not operate the GPU. The same inputs produce the same plan, so it can be checked without opening a window. Before execution, the plan is lowered to a representation the renderer can consume.

02

Pair a target with its projection

The shadow reader uses the projection that wrote the shadow. Observation target keeps this relationship; the C boundary also passes the image and map together.

The public API cannot replace one field of a validated plan. Its internal representation stays opaque.

03

Lower at one boundary

Transforms use Double; box boundaries use Rational. Validated packets contain finite Float values for the native renderer.

C owns GPU resources and executes the plan. It does not independently reconstruct the projections.

03 / Composition

Assemble the boxes before extracting their boundary

Concatenating the meshes of two touching boxes retains the faces at their contact. Extracting the boundary after assembly omits those hidden faces.

Assembly and boundary extraction cannot be reordered. The collection of boxes and the renderable mesh have different types.

The algorithm handles axis-aligned boxes. Where several materials cover the same exterior surface, the later part takes precedence.

The contact is internal, so no faces are generated there.

Exact boundary calculations

The railcar's 71 boxes use Rational coordinates. Exact comparisons reduce them to 739 exterior rectangles. Including the wheels, the 1,798 triangles are generated once and retained for reuse.

05 / Verification

Check what happens beyond the types

Distinct coordinate types do not make matrix entries or GPU transfers automatically correct. Property tests and independent reference calculations are complemented by checks of emitted geometry and actual GPU output.

What this establishes

These are finite tests and observations on a particular GPU. Static terrain and vegetation still have a path that loses precision when distant world coordinates become Float. The railcar's result does not generalize to the entire world. The reference documents the numerical results, conditions and remaining limits.

What Haskell contributes

Concrete geometry, precision and shadow fixes improved the image. Haskell expresses those calculations as pure values and functions. Types and the public API prevent mismatched spaces and partial changes to validated plans. Actual output checks cover the GPU boundary.

Other languages can express this design. In Stillroom, functional tools make the relationships visible in code and let us check them again after a change. Extracting a general graphics library remains future work.
